# 家庭三维重建方案调研与选型建议

> 编写日期：2026-10-02。针对"模型非常不靠谱、需要质量更好且后续支持导航的开源项目"这一诉求，基于项目当前真实状态与公开资料整理。
> 结论先行：**当前最该换的不是 SLAM 库，而是把 ARCore 位姿真正用起来，并允许优化后重新融合几何。**

## 1. 先诊断：现在的模型为什么"不靠谱"

依据 `docs/RTABMAP_MIGRATION_PLAN.md` 的真机记录（第 70–74 行），问题链条是清楚的：

| 现象 | 实测数据 | 根因 |
|---|---|---|
| 单体 TSDF 有孔洞、重影、表面消失 | — | TSDF 融合是"一次性"的，位姿图优化后**无法把历史帧重新融合**，错误轨迹被永久烧进体素 |
| RTAB-Map 帧接受率极低 | 364 帧只接受 1 个姿态（0.55%） | 录制线程被 Open3D 网格阻塞，约 1 帧/秒，手机转动后相邻帧跨度过大（已部分修复） |
| 短子图碎裂 | 253 帧分成 24–25 个子图、50–86 条回环 | 跟踪丢失后坐标跳变 → 每段连续轨迹被切成独立子图 |
| 主连通覆盖率低 | 40–92 帧（16%–36%） | 子图之间几何没对齐，导航门限 60% 达不到 |
| 网格视觉碎裂 | 早期下发过 35.18% 覆盖率的"仅供查看"网格 | 质量门不足，已加硬门禁修复 |

**关键判断：ARCore 的位姿本身不差。** 手机上 ARCore 已经在做 IMU+视觉+深度融合，精度足够。问题出在：

1. RTAB-Map **没有把 ARCore 位姿当先验用**（项目文档自己指出：官方 `rtabmap-rgbd_dataset` 只把 `groundtruth.txt` 用于误差评估）；
2. 于是 RTAB-Map 自己重估位姿，与 ARCore 的位姿**互相冲突**，优化的不是你已经在用的坐标系；
3. 一旦跟踪丢失产生子图，这些子图之间缺少全局一致的约束。

所以换一个新的"更强 SLAM"未必能解决——如果新库同样忽略 ARCore 位姿，同样会出现短子图。

## 2. 候选开源方案横向对比

筛选条件：开源、可在 **Windows 11 原生**或本机已有工具链上运行、支持 RGB-D、后续能产出可通行信息。

| 方案 | 类型 | Windows | 显存/算力 | 外部位姿先验 | 可通行输出 | 适配本项目 |
|---|---|---|---|---|---|---|
| **COLMAP 4.2** | SfM + MVS | ✅ 官方预编译（含 CUDA 版） | CPU 可跑，CUDA 加速；MVS 较慢 | ⚠️ 需改源码（colmap-gps 式扩展）才能真正约束 | ❌ 需自行转换 | ★★★★☆ 质量最高 |
| **VGGT / VGGT-Ω** | 几何基础模型（离线） | ✅ Python | ~12 GB VRAM @ 32 帧 504×378；<1 秒 | ❌ 自己重估位姿 | ❌ 需自行转换 | ★★★☆☆ 需降规格 |
| **MASt3R-SLAM** | 实时密集 SLAM | ❌ Ubuntu 主 / WSL 实验性 | 8 GB 最低，12 GB+ 推荐 | ❌ | ❌ | ★★☆☆☆ 违背无 WSL 约束 |
| **Pi3** | 几何基础模型 | ✅ Python | 24 GB @ 100 帧 | ❌ | ❌ | ★☆☆☆☆ 显存不够 + 权重 NC 不可商用 |
| **DUSt3R** | 两视图重建 | ✅ Python | 8–16 GB | ❌ | ❌ | ★★☆☆☆ 需多视图融合后处理 |
| **nvblox** | GPU TSDF+ESDF | ❌ 主要 Jetson/Linux | GPU | ✅ 可指定位姿 | ✅ ESDF 专为路径规划 | ★★☆☆☆ 需 ROS/CUDA |
| **voxblox** | CPU TSDF+ESDF | ⚠️ 需自行编译 | CPU（20 cm 体素 56 ms/帧） | ✅ | ✅ | ★★★☆☆ 需编译 |
| **Open3D + g2o/gtsam** | 自建位姿图 | ✅ Python 原生 | CPU 足够 | ✅ 完全可控 | ✅ 自行构建 | ★★★★★ 最贴合 |

（★ 为在本项目约束下的适配度，不是项目本身的通用评价。）

### 2.1 重点候选补充说明

**COLMAP**（`colmap.github.io`，BSD 许可）
- 官方提供 Windows 预编译包 `colmap-x64-windows-cuda.zip`，也可用 `pip install pycolmap-cuda12`。
- 4.0 起集成 GLOMAP 全局 SfM（一次性求全部位姿，比增量快得多，正对"短子图碎裂"），并加入 ALIKED/LightGlue 学习特征；4.1 引入 Casper GPU 光束平差；4.2 支持多组件全局映射。
- **限制**：导入完整的 6DoF 位姿先验不是开箱功能，需要参考 `colmap-gps` 的改法或用 `model_importer` 灌入初始模型；室内纯色墙面/弱纹理场景特征可能不足。

**VGGT**（Meta + 牛津，CVPR 2025 最佳论文，CC-BY）
- 输入若干张无位姿图片，一次前向输出所有位姿、深度、点图、内参，**不需要标定**。
- 显存约 12 GB @ 32 帧 504×378；在 8 GB 卡上需要减少帧数或降分辨率（分辨率必须是 14 的倍数）。
- 优点是**全局一致几何**，天然不会出现"子图各自为政"。
- 风险：尺度只是弱先验（论文实测尺度有偏差），且它重估位姿而非使用 ARCore 位姿。

**MASt3R-SLAM**（2025）
- 实时流式 + 回环，思路最接近"边走边建"。
- 但官方明确：Ubuntu 为主，WSL 为实验性（且需切 `windows` 分支关闭多进程），**原生 Windows 不支持**；检查点 5–6 GB；8 GB 显存是最低而非推荐值。

**nvblox / voxblox**（导航级距离场）
- 解决的是"从表面得到 ESDF 用于避障"，**不解决位姿漂移**。
- 你现在的瓶颈在位姿，不在这里。等位姿可靠后再考虑，比现在上更划算。

## 3. 推荐路线

### 主推：ARCore 位姿作主约束 + 全局位姿图优化 + 关键帧重融合

这是唯一能同时解掉"孔洞重影""子图碎裂""覆盖率低"三个问题的路线，而且完全在 Windows 上、CPU 就能跑：

1. **保留 ARCore 位姿**：相邻帧的相对位姿作为位姿图的强边（置信度高，不需要怀疑）。
2. **回环边**：用重叠 RGB-D 关键帧做 3D 特征匹配/ICP 估计约束（项目里 `tools/relocalization` 已经在做分段刚体变换，方向正确）。
3. **全局优化**：用 g2o 或 gtsam 求解位姿图；ARCore 位姿与回环冲突时以回环为准修正整图。
4. **重新融合**：优化后的位姿回灌关键帧，**重新生成 TSDF/网格/占据**——这一步是当前方案缺失的关键，也是孔洞重影的根因。
5. **导航层**：在可靠支撑面上生成可站立节点与边，输出可通行图（项目已有 `cognition/navigation.json` 设计）。

配套工具：
- 位姿图：Open3D `PoseGraph` 或 gtsam / g2o；
- 重融合：Open3D `ScalableTSDFVolume`（Python 直接调用，Windows 原生）；
- 特征匹配：LoFTR（更适合弱纹理）/ SuperPoint+LightGlue（COLMAP 4.0 已集成）。

### 备选：COLMAP 作为质量上限验证

用同一批家庭扫描帧跑一遍 COLMAP（Windows 预编译版），看它能否把 253 帧重建成一个连通模型。
- 若 COLMAP 能连通 → 说明数据本身没问题，主推路线可以放心做；
- 若 COLMAP 也碎裂 → 说明是采集覆盖不足（转头太快、重叠不够），应先改采集端节奏。

这一步成本低（下载即用），建议**先做**，它能直接回答"数据够不够"这个最关键的问题。

### 可选：VGGT 作为兜底/交叉校验

若后续愿意降显存（8–12 帧一批 + 分辨率减半），VGGT 可作为**独立第三方几何证据**，与主路线结果比对。不一致时说明该区域可疑，正好可以驱动"补扫提示"。

## 4. 立刻可做的三件事

1. **采集端先改节奏**：用户转头太快是主因之一（相邻帧跨度过大导致帧拒绝）。建议采集时保持"慢、小步、每次转一点就停 0.5 秒"，并确认关键帧门限（当前 3 cm / 2.5° / 0.20 s）。
2. **跑 COLMAP 验证数据可用性**：把家庭扫描的关键帧（RGB + 真实内参）喂给 COLMAP Windows 版，看主连通率。这是投入产出比最高的一步。
3. **不要在当前 RTAB-Map 路径上继续加码**：官方位姿先验缺失是架构级限制，靠调参解决不了；除非愿意自己改 rtabmap 源码（与"不引入新依赖"的初衷冲突）。

## 5. 许可与风险提示

- COLMAP：BSD，可商用。
- VGGT：代码与权重 CC-BY；Pi3 权重为 CC BY-NC 4.0（不可商用），本项目若考虑商用应避开。
- MASt3R / DUSt3R：研究许可居多，商用需核对。
- 所有方案都**不能**替代盲杖与人工确认；地图只能标注为"候选可走"。
