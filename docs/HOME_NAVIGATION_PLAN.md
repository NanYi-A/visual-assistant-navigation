# 家庭地图与室内导航项目规范

版本：2.0；更新日期：2026-10-01；状态：最终产品目标已确认，分阶段实现。本文是家庭建图、用户语义标注、自动识别家庭、跨会话定位和安全引导的范围与验收依据；历史 README 的局部扫描功能不代表家庭导航已实现。

## 1. 用户目标与首条路线

在家人协助下一次性扫描家庭环境，之后重新打开应用，通过普通相机观察重新确定所在位置和朝向。用户说“去卫生间”，系统规划路线，持续更新位置、检查临时障碍，通过简短语音和振动引导到门口。

第一条验证路线限定为卧室—走廊—卫生间，单层、有人陪同测试。首版不覆盖楼梯、电梯、室外导航，不承诺地面湿滑、玻璃、坑洞等均可识别。不把漂亮点云、识别房间或测试通过等同于可独立使用的导航产品。

## 2. 已有系统与需要替换的假设

现有 Kotlin 应用有 CameraX 本地目标检测、Vosk 语音输入、TTS/振动，以及 ARCore 原始深度局部扫描。局部扫描只保留约 15 秒表面，退出后清空，没有跨会话定位、持久家庭地图、地面通道或路线规划。

保留已有识别模式。新增家庭采集必须由用户明确启动，普通扫描仍不落盘。历史障碍消失、Wi-Fi 相同、识别到“床”、点云空白均不能证明位置准确或道路可走。

## 3. 系统分工

1. Android：采集 RGB、内参、时间戳、ARCore 位姿；实时视觉惯性跟踪；近处障碍提醒；语音操作；后续加载轻量导航地图。
2. 本地电脑：运行 LingBot-Map 离线重建；几何质量检查、尺度对齐；关键帧索引和三维特征关联；初期重定位计算。优先本地网络，不默认上传公网。
3. 定位模块：图像检索得到候选地点，局部特征匹配及 2D–3D 几何求解，多帧一致性验证；点云配准只用于辅助确认。hloc 是候选实现，尚未完成与 LingBot 输出适配。
4. 导航模块：房间/门口连接图负责全局路线；地面可通行栅格负责局部路线；当前障碍覆盖静态地图。手机方向和身体方向分开处理。

LingBot-Map 是几何重建后端，不是现成的持久地图重定位或视障导航服务。不得假定模型输出已经是经过验证的米制坐标。

## 4. 地图内容及坐标约定

家庭地图版本包含：mapId、修订号、采集来源、关键帧图片和相机参数、相机位姿、稀疏特征到三维点的关联、稠密表面、尺度校准记录、房间/门口标签、可通行/占用/未知区域、人工检查记录。

采集格式 v1：manifest.json + frames.jsonl + images/*.jpg。每个采集包只允许一个连续 ARCore 坐标系；暂停、跟踪丢失或位姿跳变立即结束采集，禁止无说明拼接两段位姿。RGB 保存传感器原方向、不应用显示旋转；K 是缩放后 JPG 对应的内参。cameraToWorld 为列主序 4×4，ARCore/OpenGL 右手坐标，相机 +X 右、+Y 上、-Z 前；图像像素 x 右、y 下。导入其他库时必须显式转换相机轴，不可直接混用 OpenCV 的 +Z 前。

frameTimestampNs、imageTimestampNs 分开记录，elapsedRealtimeMs 用于本次采集时间，不作为跨设备时钟。记录相机 ID、传感器旋转和原始图像尺寸；不宣称图像和位姿天然完全同步，导入前检查时间差。首期不保存原始深度图；AR 位姿提供尺度对齐候选，但需实测门宽/距离作为独立验收。

采集包不是成品地图；readyForNavigation 必须为 false。失败/中断的包保留原因，可用于诊断；只有用户正常结束且达到数量门槛的包才允许进入重建准备阶段。

## 5. 用户流程与无障碍

### 建图
由家人陪同采集第一条路线，保持画面清晰，观察门框、地面、墙角等稳定结构。初版在空间扫描页提供“采集家庭路线”“完成采集”“导出采集包”。启动时告知本地保存图片；播报开始、定期进度、结束、跟踪中断和保存失败。不把采集过程当作导航。

### 日常定位（后续阶段）
家庭 Wi-Fi/粗位置只筛选地图，不作为定位成功条件。观察当前画面；不足时语音提示缓慢观察门口等稳定结构。至少多帧几何一致后进入定位成功。应用重启后不得沿用旧位姿。记录 T_map_from_session，随 ARCore 跟踪更新，周期性重新匹配纠偏。

### 导航（后续阶段）
语音选择目的地→确认可靠定位→检查路线→分段提示→当前障碍触发停下/重规划→到门口再次确认。危险提示优先于路线和状态提示，旧转向提示不排队。持机朝向不稳定时要求重新对准，不能据此误报用户转弯完成。

## 6. 状态及失败处理

采集：IDLE → RECORDING → SAVING → SAVED/INCOMPLETE/ERROR。写盘异步、有界队列，忙时丢采样帧，不能无限积压；限制 600 帧、最多 5 分钟、低磁盘停止。帧文件先成功写入，再追加记录；manifest 最后原子替换。进后台结束当前采集，不自动恢复记录。

未来定位：NO_MAP → SEARCHING → VERIFYING → LOCALIZED → LOST。地图版本、几何一致性、位置/朝向误差或数据新鲜度任一不合格，不输出行走指令。不可直接从“搜索到相似照片”跳到导航。

未来导航：IDLE → ROUTE_READY → GUIDING → BLOCKED/LOCALIZATION_LOST → ARRIVED。未知空间不可作为默认通路；障碍膨胀包含人体宽度、持机偏移和定位误差。静态地图不能覆盖当前关门/障碍证据。断网、结果过期、相机关闭时撤销路线指令，保留本地提醒。

## 7. 分阶段交付与验收门槛

## 8. 隐私、容量和工程约束

家庭图片默认只保存在应用私有目录，用户主动导出到自己选择的位置；无需为 M1 新增网络权限。导出的 ZIP 含家庭影像，界面应明确说明。保留当前未导出的采集，不静默覆盖。清理操作与采集停止不同，不自动删除用户数据。M1 限制每包容量/帧数，后续提供地图管理和删除。

模型不打包进 APK；大型权重单独放电脑。接口通过有版本的数据契约隔离，允许重建后端替换。后台任务失败要产生可读错误，不返回空地图冒充成功。重定位网络服务上线前必须增加配对认证、超时、地图版本校验，不裸露家庭图片服务。

## 9. 本轮实现范围与后续依赖

本轮先实现 M1 的代码和自动验证，准备 M2 可复现入口。M2 实测需要一段真实、覆盖卧室—走廊—卫生间的采集；桌面静止画面不能替代。M3/M4 在 M2 数据质量过关后实施，不在没有真值的情况下编造定位效果。

每次改动更新 PROGRESS.md：实际完成、测试命令、真机证据、未通过项与下一步。新需求先映射到阶段；不得把未完成的重定位/导航按钮包装为成品能力。

## 11. 最终产品闭环（2026-10-01 用户确认）

系统必须完成以下闭环，而不是只展示彩色网格或占据体素：

1. 家人进入“采集家庭”模式，连续扫描全部需要导航的房间、门洞、走廊、楼梯和关键地面。
2. 电脑生成同一家庭坐标系中的彩色模型、视觉定位地图、三维占据证据、可站立表面和导航图。
3. 房间名称与目的地语义全部来自用户现场口述标注；系统不得根据床、马桶或餐桌擅自猜测房间名称。
4. 日常打开应用时先进行短时被动观察，判断当前画面是否属于某个已保存家庭。只有多帧几何验证通过，才能自动进入对应家庭导航。
5. 进入家庭导航后，系统输出用户在家庭地图中的三维位置和面朝方向，并持续用视觉重定位纠正 ARCore 漂移。
6. 用户说“我想去卫生间”后，系统解析到用户确认过的“卫生间”目标区域，规划全局路线。
7. 行走过程中，静态家庭导航图提供全局方向；手机实时深度和 YOLO 检查近处临时障碍。路线被挡时先让用户停下，再局部绕行；局部无法绕过时重新规划全局路线。
8. 定位、地面、净空、实时障碍或路线新鲜度任一不满足安全门槛时，只允许播报停止和补扫指令，不得继续给出向前走指令。

## 12. 用户口述房间标注

### 12.1 硬约束

- 所有房间名、区域名和目的地名均由用户提供并确认。
- YOLO 可以描述“看到床、桌子、马桶”，只能辅助用户理解现场，不能自动把区域命名为卧室、餐厅或卫生间。
- 一个名称可以有用户确认的同义词，例如“卫生间/厕所”；冲突名称必须要求用户选择，不能静默覆盖。

### 12.2 标注流程

1. 家庭几何扫描达到最低覆盖率后，应用进入“标记地点”。
2. 语音引导用户走到目标房间内安全、开阔且便于以后抵达的位置，不要求贴近墙角或家具。
3. 用户站定并缓慢环视；系统必须先确认当前定位稳定、所在可站立连通区域明确。
4. 应用提示“请说这里是什么地方”；用户说“这是卧室”“这里是餐厅”或“这是卫生间”。
5. 语音识别后必须复述：“将这里标记为卫生间，是否正确？”用户回答确认后才写入地图。
6. 一个地点标记保存：名称、同义词、用户站立位姿、面朝方向、所属可站立区域、多帧视觉锚点、定位置信度、创建时间和地图版本。
7. 标注完成后播报已保存名称，并引导用户前往下一个未标注区域；用户可以说“重新命名”“删除这个标记”“重新采集这个房间”。

### 12.3 区域边界

口述发生的位置只是语义锚点，不把一个点当作整个房间。后端以该锚点所在的可站立连通面为种子，根据墙体、门洞和地面连接提出区域边界；家人在手机彩色模型上确认或调整。未经确认的扩展区域保留为“未命名区域”。目的地默认是房间内离门口有安全余量的可站立到达区，不是用户录音时脚下的单一坐标。

### 12.4 数据结构

```json
{
  "placeId": "uuid",
  "name": "卫生间",
  "aliases": ["厕所"],
  "userConfirmed": true,
  "anchorPoseMap": {"x": 0, "y": 0, "z": 0, "yaw": 0},
  "regionId": "walkable-region-id",
  "arrivalZoneIds": ["safe-zone-id"],
  "visualAnchorIds": ["keyframe-id"],
  "mapRevision": 1,
  "createdAt": 0
}
```

## 13. 家庭识别与跨会话六自由度定位

家庭识别和精确定位分为两级，禁止只凭 Wi-Fi 或物体类别自动进入导航：

1. **候选筛选**：已配对电脑、可选家庭 Wi-Fi 指纹、最近使用记录和图像全局描述子只用于缩小候选家庭。
2. **几何验证**：连续关键帧与家庭视觉地图进行局部特征匹配，通过 2D–3D PnP/RANSAC 得到位置和朝向；至少三帧结果在位置、旋转和重投影误差上连续一致。
3. **坐标对齐**：建立 `T_home_from_ar_session`，把当前 ARCore 坐标变换到家庭地图坐标。ARCore 提供低延迟相对运动，视觉地图周期性纠偏。
4. **运行期监控**：记录最近一次几何验证时间、内点数、重投影误差、位置协方差和朝向误差。置信度不足进入 `LOCALIZATION_LOST`，立即撤销行走指令。
5. **非家庭画面**：未匹配任何家庭时保持默认户外即时扫描，不把“识别失败”当成“家里发生变化”。

状态机：`SEARCHING_HOME → VERIFYING_HOME → LOCALIZED_HOME → NAVIGATING`；任何阶段可转入 `NOT_HOME` 或 `LOCALIZATION_LOST`。

## 14. 从三维模型生成可导航认知

原始红绿黄紫体素只是传感器证据，不能直接规划路线。后端必须生成以下派生层：

- 重力对齐的地面、坡面、楼梯踏步和落差边缘；
- 可站立表面及坡度、粗糙度、台阶高度和观测置信度；
- 从脚面到头部的三维净空；
- 按用户身体半径、持机偏移、定位误差和安全余量膨胀后的碰撞体；
- 门洞有效宽度、头部净高和开闭/遮挡状态；
- 多楼层/楼梯连接的三维导航图；
- 未观测区域永远保持未知，不能通过网格补洞转成可走。

全局路线只允许经过已确认可站立且净空足够的节点和边。彩色补面只用于家人查看，不能进入碰撞或导航计算。

## 15. 语音目的地与行走引导

1. 用户说“我想去卫生间”。语音层只匹配用户确认的地点名和同义词。
2. 系统复述起点、目标和当前定位状态；存在重名时要求用户选择。
3. 全局规划器在三维导航图上计算路线，代价包含距离、转弯、窄通道、坡度、楼梯和低置信区域；未知区域不可通行。
4. 手机只接收前方若干航点和走廊边界，并将其变换到当前 AR 坐标系。
5. 提示采用“先方向、再距离、再动作”的短句，例如“向右转约四十度，前进两米到门口”。旧提示在新定位或障碍结果到达时立即失效。
6. 到达房间的安全到达区后，通过位置、方向和现场视觉锚点再次确认，再播报“已到卫生间”。

## 16. 动态障碍与绕行

- 实时 ARCore 深度负责几何距离和脚前方/身体高度碰撞；YOLO只负责给可见物体命名。
- 动态障碍覆盖静态家庭地图，检测到路线走廊被占用时首先播报停止，并冻结旧的“继续前进”提示。
- 在当前已观测、可站立且净空足够的局部区域内寻找绕行走廊；未扫到的侧面不能被当作可绕行空间。
- 局部绕行重新接回全局路线后，明确播报何时转回以及何时可以继续直行。
- 若两侧均未知、障碍持续、定位丢失或用户偏离地图，要求停下并缓慢补扫；不得用历史绿色区域覆盖当前障碍。

## 17. 模型库最终形态

每个家庭模型详情应包含：

- 家人查看的真实彩色模型；
- 工程用占据证据；
- 用户可理解的地面、墙、门、楼梯、不可走体积和路线视图；
- 用户口述地点列表及在模型中的标记；
- 覆盖缺口、冲突区、处理状态、地图版本和最后验证时间；
- 进入标注、补扫、改名、删除、重新处理和试走验证入口。

“占据证据”不得继续命名为已经可导航的“碰撞与通行”。只有生成可站立表面、人体净空和导航图并通过验收后，才显示“可导航模型”。
