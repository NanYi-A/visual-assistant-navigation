- 版本：v1（2026-10-03）
- 状态：**S1–S4 代码层 + S6 UI/业务接线已完成，173 项单元测试全部通过，APK 已构建**；**S5 真机验收待执行**（需要本人走一遍）。2026-10-03 真机数据体检发现当前地图不连通、4 个地点坐标重合，已修复底层原因，需重新采集。
- 前置文档：`NAVIGATION_COGNITION_PLAN.md`（认知层）、`MASTER_IMPLEMENTATION_TRACKER.md`（权威清单）、`CAPTURE_HEALTH_REPORT.md`（数据体检）

## 1. 为什么要换方向

### 1.1 三次失败的共同根因

我们已经试过三条路，全部卡在同一处：

| 尝试 | 结果 | 根因 |
|---|---|---|
| LingBot 离线重建 | 推理 772 秒 / 帧，峰值 9.27 GB | 单卡跑不动，且 RGB 重建缺尺度 |
| RTAB-Map 优化 | 覆盖比原始扫描少四成，碎成 19 子图 | 官方工具不把外部位姿当前验 |
| 自动建图 + 覆盖率门 | 支撑覆盖 27%、连通率 0%，永远 `NEEDS_RESCAN` | 一次走完就要覆盖全屋，本来就做不到 |

第三条是最有价值的失败——它**诚实地告诉我们数据不够**，而不是骗我们说"完成"。

### 1.2 缺的不是算法，是地图的"生产方式"

回看目标：**让视障的人从卧室走到卫生间。**

这件事的必要条件只有三个：

1. 知道哪里能走（可通行图）
2. 知道自己是谁、在哪（定位）
3. 走路时地图不乱（跟踪稳定）

**"自动重建全屋三维模型"不在必要条件里。** 我们把力气全花在了它上面。

那些学生项目（ArNavAi、ARNav、NavigatAR、ARNavigation）能跑，是因为它们**全都放弃了自动建图，改成预先提供地图**——只不过用的是贴二维码这种偷懒办法。

我们不需要二维码。我们需要的是：**让人走一遍，把地图存下来，之后反复用。**

### 1.3 新方向

放弃"自动建图"，改为**半自动建图 + 目的地导航**：

```
建图阶段（一次性，人在场）
  人走一遍（卧室→走廊→卫生间），手机实时算栅格
  ＋ 沿途说"这是卧室"/"这是卫生间门口"打标记点
  → 存成一张持久家地图

导航阶段（反复使用）
  用户说"我要去卫生间"
  → 确认起点（说"我从卧室出发"）
  → 在持久地图上规划路径
  → 边走边播报"向前 1.5 米，左转"
  → 实时局部栅格仍然最高优先级，任何时候都能急停
```

## 2. 核心设计决策

### 2.1 家地图存手机本地，不存电脑

| 维度 | 手机本地 | 电脑 |
|---|---|---|
| 可用性 | 断网也能用 | 必须连电脑 |
| 延迟 | 毫秒级 | 网络往返 |
| 隐私 | 家庭数据不出手机 | 要传出去 |
| 实时急停 | 天然满足（本地传感器） | 不可能 |

**结论：导航闭环必须在手机本地完成。** 电脑只保留彩色模型给家人看，以及建图后的质量报告。

### 2.2 复用已有的 2.5D 栅格，不引入新算法

`SessionGridMemory` 的格子**已经是 ARCore 世界坐标**（`worldX`/`worldZ`），已经解决了"走近后旧地图消失"的问题。它缺的只有一件事：**会话结束后会丢**。

所以 S1 不是写新算法，是给现有格子加一个持久化层。这是本方案最大的成本优势——**大部分代码已经存在且经过真机验证**。

### 2.3 坐标系策略：标记点即锚点

ARCore 世界坐标系在每次会话重启后都会重置（原点、方向都变）。跨会话对齐有三条路：

| 方案 | 精度 | 成本 | 结论 |
|---|---|---|---|
| 视觉重定位（拍门牌、纹特征） | 高 | 高，且白墙环境失效 | 不用 |
| WiFi/蓝牙指纹 | 中 | 需要预埋设备 | 不用 |
| **人工标记点 + 2D 刚体变换** | 取决于标记点间距 | **极低，说一句话** | **采用** |

具体做法：用户在地点 A 打标记，ARCore 记下 `T_worldA_A`。下次会话用户在 A 说"我在卧室"，即认为新会话的某点等于旧地图的 A。**单标记点只能定平移，两个不共线标记点才能定朝向。**

**诚实边界：单标记点对齐时朝向未知。** 首次实现只支持"用户同时给出两个标记点"或"沿已知走廊方向行走时用 IMU 推算朝向"。宁可承认朝向不确定，也不能编一个假方向让用户走错。

### 2.4 目的地寻址靠标记点，不靠语义理解

用户说"卫生间"→ 在家地图的标记点列表里找名字匹配的 → 找到就规划，找不到就**明确说"地图里没有标记卫生间，请先扫描时标记一下"**。

不做房间语义识别、不做物体识别定位。这一版的目标是"能走到门口"，不是"知道那是卫生间"。

## 3. 分层结构

```
┌─ 实时层（会话内，最高优先级，永不下放）──────────────┐
│  SpatialMap / SessionGridMemory / LocalNavigator    │
│  职责：急停、绕行、脚下地图                        │
│  延迟要求：P95 ≤ 200 ms                            │
└────────────────────────────────────────────────────┘
                        ▲ 覆盖
┌─ 家地图层（跨会话，本方案新增）─────────────────────┐
│  HomeMap：持久化的世界格 + 标记点                  │
│  HomeRoutePlanner：A* 全局路径                     │
│  HomeNavigationSession：请求生命周期 + 语音播报    │
└────────────────────────────────────────────────────┘
                        ▲ 只读参考
┌─ 电脑层（离线，非导航必需）────────────────────────┐
│  彩色模型（给家人看）+ 认知层覆盖率报告             │
└────────────────────────────────────────────────────┘
```

**硬边界：实时层永远可以否决家地图层的任何结论。** 家地图说"前面能走"，实时层说"前面有障碍"，以实时层为准。这条不能破。

## 4. 实施步骤

### S1：HomeMap 持久化（存储层）

- 格子格式：沿用现有 10 cm 世界格，`(indexX, indexZ) → (state, evidence, minHeight, maxHeight)`
- 写入：**原子写**（临时文件 + rename），带版本号与校验和；损坏时回退到上一份备份而不是崩溃
- 合并：新会话的格子并入已有地图；旧障碍需连续 6 次自由观测才改回自由（沿用现有规则，不得放宽）
- 标记点：名字 + 世界位姿 + 朝向，存同一份文件

**验收**：写入后重启 App 仍能读出全部格与标记点；人为截断文件后能自动回退且不崩溃。

### S2：跨会话对齐

- 单标记点：只定平移，朝向标记为"未知"，导航只报距离不报左右
- 双标记点：解 2D 刚体变换（平移 + 旋转），精度取决于两点间距，间距 < 0.5 m 时拒绝并要求重新标记
- 对齐残差 > 0.5 m 时**拒绝导航**并要求人工确认

**验收**：给定已知变换的合成数据，对齐误差 < 5 cm；两点共线时明确报错而非静默给出错误朝向。

### S3：HomeRoutePlanner（A* 全局路径）

- 栅格：10 cm，八邻域，对角代价 1.4（与 `LocalNavigator` 一致）
- 禁止斜穿两个障碍之间的对角缝（与现有 `NEIGHBORS` 判据一致）
- 代价函数：距离 + 窄口惩罚（宽度 < 0.45 m 加权）+ 未知区惩罚（不禁止，但加权让人主动避开）
- 输出：路径点列 + 分段指令（前进距离、转向角度、是否窄口）
- **不可达时必须给出具体原因**：是"没有任何已知通路"，还是"通路被未知区域截断"，还是"通道宽度不足"。三者对用户的下一步动作完全不同。

**验收**：合成地图上规划出的路径不穿越障碍；窄口被正确加权；三类不可达原因可区分。

### S4：HomeNavigationSession（状态机 + 语音）

生命周期：`请求 → 确认起点 → 规划 → 行走中 → 到达 / 偏航 / 卡住 / 放弃`

- 到达判定：距目标 < 0.8 m 且地图可信
- 偏航检测：连续 3 次实际前进方向与指令偏差 > 45°，提示"可能走偏了，请确认方向"
- 卡住检测：30 秒内位移 < 0.3 m，提示"似乎没有前进，请确认是否被挡住"
- 语音优先级：`NAVIGATION`，不打断问答与危险提示
- **到达播报必须包含不确定性**："已到达标记点附近，请确认这是不是卫生间门口"——不能说"你已到卫生间"

**验收**：状态机每个状态可被单测驱动；语音不重复刷屏（同 key 去重）；任何异常都能回到"待命"而不是卡死。

### S5：真机验收

- 走一遍完整路线并沿途标记 3–5 个点
- 结束会话 → 重启 App → 地图与标记点仍在
- 说"我要去卫生间" → 走完全程
- 故意说错起点 → 必须被拒绝或明确要求确认

### S6：UI / 业务接线（已完成）

把 S1–S4 的三个类接进 `SpatialActivity`，让功能在手机上真的能被触发：

| 接线点 | 位置 | 说明 |
|---|---|---|
| 栅格全量导出 | `SpatialMap.SessionGridMemory.allCells()` + `SpatialRenderer.exportGrid()` | 原有的 `update()` 只返回相机 6 m 内的格子，不足以存图；新增全量导出并加 `@Synchronized`（GL 线程写、主线程读） |
| 落盘家地图 | `SpatialActivity.persistHomeMap()` | 在 `stopScan()` 里、**`renderer.clearMap(true)` 之前**调用；`onDestroy()` 也有兜底，被杀后台不丢整趟 |
| 语音指令 | `handleVoiceResult()` 前置 `handleHomeNavigationCommand()` | 「我要去 X」「导航到 X」「带我去 X」「我在卧室，要去卫生间」「停止导航」 |
| 导航推进 | `voiceTick` 新增分支 → `advanceHomeNavigation()` | 每 500 ms 喂位置，播报走 `say(text, NAVIGATION, "home-nav")`；**不依赖 `scanning`**，采集结束后仍能导航 |
| 按钮入口 | 「去某个标记地点」 | 语音不可用（嘈杂/麦克风被占）时仍可进入；会先播报已标记地点清单 |
| 库页面状态 | `HomeModelLibraryPage` | 每个模型显示「家地图已就绪 · 覆盖 N 格」或「家地图尚未建立」 |

优先级约束：所有导航播报固定 `SpeechPriority.NAVIGATION`，只有 `EMERGENCY` 能抢断——**记住的路线永远压不过传感器现在看到的东西**。

## 5. 必须诚实面对的边界

这一节是本方案的红线，**任何 UI 文案都不得违反**。

| 边界 | 说明 | 文案约束 |
|---|---|---|
| **起点必须人工确认** | 系统无法自动知道你在哪，这是物理限制不是实现缺陷 | 必须说"请说你从哪出发"，不能假装自动定位 |
| **地图可能陈旧** | 家具挪动后旧地图失效 | 导航中若实时层与家地图冲突，**必须提示"家具位置可能已变化"**，不能静默按旧地图走 |
| **不是安全保证** | 家地图只能说明"上次看到时可通行" | 绿色区域一律称"候选可走区域"，禁止"安全/可以放心走" |
| **未知就是未知** | 没扫过的地方不能推断 | 覆盖率不足时必须说"这段路还没有确认过"，不能给方向 |
| **朝向可能未知** | 单标记点无法定朝向 | 此时只报距离，**禁止报左右转** |

## 6. 明确不做的事

写清楚边界，避免再次陷入无止境的方案探索：

- ❌ 自动重建全屋三维模型（已证明不可行）
- ❌ 视觉重定位 / 纹理匹配（白墙环境失效）
- ❌ 房间语义识别（"这间是卧室"）
- ❌ 跨楼层 / 楼梯引导
- ❌ 实时避障交给家地图（必须由实时层承担）
- ❌ 云端服务、数据上传（数据主权原则）

## 8. 未决事项（等真机数据说话，不先拍板）

1. **格子的长期存储格式**：二进制紧凑格式 vs 直接复用现有对象序列化。取决于实测地图大小（预计 2 万–5 万格）。
2. **标记点间距门槛**：目前定 0.5 m，需真机验证用户在门口能否稳定打出两个足够远的点。
3. **地图膨胀策略**：家具挪动后是要求重扫局部，还是允许自动降级为未知。倾向前者（更诚实），但需确认用户可接受。
4. **是否需要"回家自动重定位"**：即用户完全不确认起点时的可行性。当前判定为不可行，保留但不做。

## 9. 已实现的接口（S1–S4 代码层）

供后续接 UI 与真机验收时对照。全部为纯 JVM 逻辑，可在无手机环境下测试。

### 9.1 `spatial/HomeMap.kt`

| 成员 | 职责 |
|---|---|
| `HomeMapCell` | 单个 10 cm 世界格：占据标记、证据数、高度上下界 |
| `HomeMapAnchor` | 用户语音标记的命名地点（名字 + 世界位姿 + 朝向） |
| `HomeMapAlignment` | 地图→世界的 2D 刚体变换；**`headingKnown=false` 时禁止报左右转** |
| `HomeMap.mergeObserved()` | 把当前会话观测并入地图；旧障碍需连续 6 次自由观测才改回自由 |
| `HomeMap.findAnchorByName()` | 精确名优先，否则唯一子串匹配；**多个匹配时返回多个，由上层拒绝** |
| `HomeMap.applyAlignmentInPlace()` | 跨会话后把地图整体搬到新的世界坐标系 |
| `HomeMapStore.save()` | 原子写（临时文件 → rename），保留上一份为 `.bak` |
| `HomeMapStore.loadWithSource()` | 主文件损坏时自动回退备份，返回来源供诊断 |
| `HomeMapRelocalizer.alignBySingleAnchor()` | 单标记点：只解平移，**朝向标记为未知** |
| `HomeMapRelocalizer.alignByTwoAnchors()` | 双标记点：解 2D 刚体变换；间距 < 0.5 m 或残差 > 0.5 m 时**拒绝** |

### 9.2 `spatial/HomeRoutePlanner.kt`

| 成员 | 职责 |
|---|---|
| `RouteResult.Found` | 路径点列、 总长度、最窄处、分段指令、是否经过未知区 |
| `RouteResult.Failed` | 五类失败原因（`NO_START` / `GOAL_UNKNOWN` / `BLOCKED` / `TOO_NARROW` / `DISCONNECTED`） |
| `HomeRoutePlanner.plan()` | A*，八邻域，对角 1.4，窄口加权，禁止斜穿双障碍对角缝 |
| `RouteLeg` | 一段指令：前进距离、转向角度、是否窄口、该段宽度 |

**关键阈值**：最小可通行宽度 0.45 m、舒适宽度 0.9 m、起点搜索半径 0.8 m、转向播报阈值 25°。

### 9.3 `spatial/HomeNavigationSession.kt`

| 状态 | 含义 |
|---|---|
| `Idle` | 无请求 |
| `AwaitingStart` | 已知目的地，**等待用户声明起点**（这是本方案的核心人工步骤） |
| `NeedsAlignment` | 起点无法确定（未知标记 / 多个匹配 / 两点太近） |
| `Navigating` | 沿路线行进中 |
| `Arriving` | 距目标 < 0.8 m，**播报必须要求用户确认** |
| `Done` | 完成或主动停止，携带给用户看的原因文本 |

**检测能力**：地图陈旧冲突（实时看到障碍但地图说空）、卡住（30 秒位移 < 0.3 m）、走偏（连续 3 次背离路线）。

## 10. 实施过程中修正的缺陷（均有实测依据）

这些问题全部由单元测试暴露，其中前三个若在真机上发生会直接误导用户：

1. **双锚点对齐方向算反**（最危险）。`alignByTwoAnchors` 里 yaw 写成 `worldHeading − mapHeading`，而 `mapToWorld` 的旋转约定要求 `mapHeading − worldHeading`。同时 `Pair` 的 `.first`/`.second` 被交叉取值（一个取 x 另一个取 z）。两者叠加会让算出的朝向完全错误，且残差检验会因此拒绝或静默接受错误结果。**已修正并补齐正向/逆向映射的双向断言。**
2. **未知朝向时仍然播报转向**。原实现只压制"第一段"的转向，但整条路径的转向都是地图坐标下的角度——朝向未知时**任何**转向都无法换算到用户坐标系。已改为整条路线统一压制，只报距离。
3. **到达播报永远发不出去**。`update` 在到达分支直接 `return null`，语音被吞掉，用户会以为手机卡死。已改为由 `speak()` 明确返回"是否真的说了"，并把"有话要说"与"这句话是否新鲜"两件事分开。
4. **偏航检测形同虚设**。原实现比较相邻两次读数，单步位移小于阈值时永远不触发；且"最近距离"被每轮无条件覆盖，缓慢偏航无法累积。已改为与历史最近距离比较，小幅持续走偏也能发现。
5. **旧障碍的清除计数不会重置**。重看一次障碍后，之前的自由观测计数仍在累加，家具会在六次"瞥见"后被误判为已挪走。已改为看到障碍即清零计数。

另有一处为**测试本身写错**（不是产品缺陷）：双锚点用例中第二个标记点被放在了地图范围之外，对齐自然无法成功——已加宽测试地图并说明原因。

### 接线阶段发现的缺陷（更严重，均已修复并补回归用例）

6. **坐标系混用（最危险）**。`HomeNavigationSession` 一直拿**家地图坐标系里的锚点坐标**和 **ARCore 世界坐标系里的当前位置**直接算距离和规划路径，而 `HomeMap.applyAlignmentInPlace()` 从来没有被调用过。之前 43 项测试全绿，只是因为测试里对齐平移恰好接近 0——真机上跨会话重定位一有平移，整条路就是错的。
   - 修法：**保持地图坐标系不动**（这样多段采集可以合并进同一张图），每轮把实时位置用 `HomeMapAlignment.worldToMapX/Z` 换算进地图坐标系。`applyAlignmentInPlace` 保留但改为注明"仅用于导出查看"，因为把地图烧进某个会话的世界坐标系会让后续会话的对齐层层叠加。
   - 新增回归用例 `theRouteIsPlannedInTheMapFrameNotTheWorldFrame` / `arrivalIsDetectedAcrossAShiftedAndRotatedFrame`：把世界平移 10 米并旋转 90°，旧实现会报出约 10 米的路程且永远到不了。

7. **"直行"是凭空假设的**。原来第一条腿的转向恒为 0（即"继续直行"），但那只是地图自身的轴向，跟人朝哪儿站毫无关系。已改为：`plan()` 接收"人在地图坐标系里的朝向"，**拿不到朝向就整条路都不说转向**（不只是第一条）。朝向要从 ARCore 位姿取水平前向，手机朝天花板/地板时前向不稳定，此时 `CameraTransform.forward` 返回 null 而不是返回一个默认值。

8. **`confirmSecondAnchor` 会从第二个锚点重新规划**（用户此时已经走到门口了）。这是正确行为，但会让人误判——已补用例 `confirmingASecondAnchorReplansFromWhereTheUserStands` 锁定它。

9. **`syncHomeMapAnchors` 不落盘且按名字匹配**。`persistHomeMap()` 调用它后丢弃返回值，保存出的 `home_map.bin` 中 `anchors=0`；同时原实现按名字匹配，改名/删除地点会留下陈旧锚点。已改为按 place id 同步，并把 `loadHomeMap()` 改成每次加载时自动同步 `places.json`。

### 真机数据体检暴露的缺陷（2026-10-03，已修复）

10. **标记地点依赖后端回传位姿，后端断开后坐标冻结**。`beginPlaceLabel()` 原本使用 `remoteCameraPose`，该变量只在 `Online3dClient` 收到电脑后端回包时更新。电脑后端 IP 配置错误或网络抖动时，位姿会停在最后一个有效值，导致用户后续标记的 客厅、阳台、一寝室 与 卫生间 完全重合（0.00m）。已改为使用本地 `renderer.currentCamera()` / `CameraTransform.fullForward`，家庭数据采集不再依赖电脑。

11. **持久化地图文件内锚点数为 0**。由于缺陷 9 的实现问题，用户手机上 `17107026230659` 模型的 `home_map.bin` 解析出 `anchors=0`，尽管 `places.json` 里有 6 个地点。`loadHomeMap()` 现在会主动把 `places.json` 同步进内存中的地图，老文件也能恢复使用。

### 语音导航故障的四个根因（2026-10-03 11:00，由真机 logcat 定位）

用户在重建家庭模型后反馈「一直掉线不让我说话，好不容易说了一次『我要去卫生间』也识别不了」。以下是完整证据链与修法。

12. **TTS 插话被麦克风录进去**。`voiceTick` 每 500ms 跑一次，条件只有 `!speaking`，不看 `voice.isListening`。手机扬声器与麦克风物理相邻，播报内容被 Vosk 当成用户说的话。日志中 10:52:01 在「请说要去哪里」之后 6 秒插入了「定位已建立，正在等待深度」。
    - 修法：整个播报块加 `&& !voice.isListening`。除 EMERGENCY 外，识别期间一律禁声。

13. **Vosk 的部分结果被当成最终结果**。原实现 `if(decoder.acceptWaveForm(...)) { result = transcript(decoder.result); if (result.isNotBlank()) break }`。Vosk 的 `acceptWaveForm` 对**中间段**同样返回 true，`getResult()` 可能是 `{"partial":...}`，一拿到非空就 break ——「我要去卫生间」只取到「我要」。
    - 修法：取所有片段中**最长**的假设；`transcript()` 兼容 `partial` 字段；识别到声音后再留 `SETTLE_MS=1.6s` 收尾窗口，避免切掉句尾；监听上限 `LISTEN_MS` 由 12s 提到 20s。

14. **`stopScan()` 无条件掐断语音**。定位 60s 超时、24s 观察倒计时结束都会调用 `stopScan()`，其中 `cancelSpeech()` 会 `voice.cancel()`。而 `VoiceInput.cancel()` 只递增 generation，回调被静默丢弃 —— 用户听到的是**彻底没有回应**，日志里连一条 `VoiceInput` 记录都没有（这正是定位该故障的关键线索：代码里有 `Log.e` 却没有记录 = 被 cancel，而非识别失败）。
    - 修法：`stopScan(userInitiated:Boolean=false)`，只有用户手动点「结束扫描」才允许掐断当前语音回合；内部超时只停采集。

15. **残留的「家庭自动定位」流程与导航抢话**。`locatingHome=true` 时会周期性重试并播报「正在建立定位…」（日志中每 15 秒一次），同时反复开关扫描，与导航对话完全重叠。
    - 修法：新增 `cancelHomeLocalization()`，由「家地图导航」按钮和 `stopScan()` 先行调用。半自动方案下这两条流程不允许并存。

**附加**：识别失败不再沉默。`onFailure` 中若正在等导航回答，700ms 后 `retryNavigationPrompt()` 会重播该说的句子并重新开麦，最多 `NAV_RETRY_LIMIT=2` 次；新增 `NavPrompt{DESTINATION,START,REALIGN}` 记录当前在等什么。新增 `SpatialVoice` / `VoiceInput` 日志，使「识别到了什么」可观测。

### 排查方法论（值得记住）

抓真机语音问题不要猜，直接看 logcat：
- `SpatialSpeech`：每条 `say()` 都会打 `speaking: <文本>`，能看到**实际说了什么、什么顺序**。
- `TtsService`：`onSynthesizeText Start/End` + `onStop` 能区分「正常说完」和「被打断」。
- `VoiceInput`：只在异常时 `Log.e`。**如果一次语音尝试在日志里既没有结果也没有错误，说明它是被 `cancel()` 掉的，而不是识别失败** —— 这个"空白"本身就是最强的线索。
