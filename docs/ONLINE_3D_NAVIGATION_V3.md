# 在线三维环境理解与闭环导航 V3

## 1. 项目目标

手机负责同步采集相机、ARCore 位姿、Raw Depth/Confidence 和本地 YOLO 结果；电脑负责三维融合、可通行空间分析和局部路线规划；手机根据自己的实时位姿执行路线并通过语音、震动引导用户。

本阶段优先级依次是：

1. 遇到近处障碍、下行台阶、跟踪丢失或数据过期时及时停止错误引导；
2. 路线和距离在移动过程中连续、可更新；
3. 在普通家居 Wi-Fi 或 USB 网络下保持低延迟；
4. 地图只需要稳定的几何轮廓，不追求照片级重建；
5. YOLO 提供“是什么”，三维系统决定“在哪里、是否挡路、能否绕行”。

系统输出始终使用“候选可通行”“请停下确认”等措辞，不能把未观测区域表达为安全区域，也不能代替盲杖、导盲犬或人工确认。

## 2. 技术选型结论

### 2.1 正式目标栈

- 手机：现有 Kotlin + ARCore；
- 传输：局域网 WebSocket 二进制帧，后续可替换 QUIC；
- 电脑环境：Windows 原生、复用现有 JDK；
- 三维融合：纯 Kotlin/JVM 稀疏体素哈希与 DDA 深度射线融合；
- 安全距离：用户周围局部窗口的近似距离场；
- 路线规划：基于人体体积的三维碰撞检查，加地面/坡面/楼梯约束的局部 A*；
- 调试显示：mesh、占据体素、规划走廊和手机位姿；
- 语义：沿用手机本地 YOLO，把检测框内深度投影到世界坐标后附加到三维对象轨迹。

轻量后端只实现导航所需的占据、自由、支撑、净空、楼梯和动态更新，不生成照片级 mesh。详细结构、存储预算和性能目标见 `docs/LIGHTWEIGHT_3D_BACKEND.md`。nvblox 保留为未来可替换的加速模块，不再要求安装 WSL2。

### 2.2 原型栈

先用现有零依赖 Python 工具接收、校验并录制手机数据，以回放方式验证坐标和深度；随后由 Kotlin/JVM 后端读取同一协议并完成实时融合与规划。Python 只用于调试，不是运行时依赖。

### 2.3 明确不采用

- 不用 NeRF 或 Gaussian Splatting 作为导航主地图：画面好看，但在线更新、自由空间和碰撞距离不是它们的强项；
- 不继续用单层 2.5D 栅格作为唯一地图：无法完整表达楼梯、桌面下方、悬空物和不同高度的空间；
- 不直接在点云上规划：点云是输入和调试表示，规划使用可更新体素与 ESDF；
- 不把手机视频压缩后交给电脑重新估计全部位姿：ARCore 原始位姿和深度更低延迟，也避免视频编码引入额外误差。

## 3. 总体架构

```text
手机 ARCore
  同一时刻的 RGB/YUV、Raw Depth、Confidence、Pose、Intrinsics
       |                      |
       | 本地急停             | 3~10 Hz 二进制上行
       v                      v
近身深度走廊            电脑接收/时间同步/质量门控
  100~200 ms 内              |
  停止/补扫                  v
                    nvblox TSDF + occupancy + decay
                              |
                              v
                       3D ESDF + 地面/台阶分析
                              |
                              v
                   人体体积碰撞检查 + 局部规划
                              |
                 10 Hz 路线增量/状态/有效期下行
                              v
手机 RouteFollower：ARCore 实时位姿投影到路线
  转向 -> 前进 -> 偏航纠正 -> 到达 -> 重新规划
```

电脑负责看得远和记得久，手机负责看得近和立即停止。任何一路发现更高风险，都能覆盖普通前进指令。

## 4. 坐标和时间约定

### 4.1 坐标系

- `session_world`：一次空间扫描启动时的 ARCore 世界坐标；
- `camera`：ARCore 相机坐标；
- `body`：以手机位置为原点、只保留重力方向和行走朝向的用户坐标；
- `map`：后端地图坐标，首次连接时与 `session_world` 对齐；
- 统一使用米、右手坐标和四元数；矩阵传输固定为 column-major，并在协议测试中使用已知点验证。

不能把手机相机朝向直接等同于用户行走方向。行走方向优先由连续位移估计；用户站定时用手机航向，并降低方向置信度。

### 4.2 时间

每个数据包同时带：

- ARCore `frameTimestampNs`；
- Raw Depth `depthTimestampNs`；
- 手机 monotonic 发送时间；
- 包序号和 session ID。

只有新的 Raw Depth 帧进入 TSDF；ARCore 重投影的旧深度可供手机近身提示，但不能重复写入地图。服务器回应包含它实际处理的输入序号、地图版本和路线生成时间，手机据此判断路线是否过期。

## 5. 上行数据协议

### 5.1 `FramePacket`

- 协议版本、session ID、frame ID；
- 设备 monotonic 时间、相机帧时间、深度时间；
- 深度宽高和图像旋转；
- `fx/fy/cx/cy`；
- `cameraToWorld` 位姿；
- Raw Depth：uint16 毫米；
- Confidence：uint8；
- 可选低分辨率灰度关键帧；
- YOLO：类别、置信度、框和跟踪 ID；
- ARCore tracking state、光照/运动质量和采集统计。

Raw Depth 160x90 时，深度和置信度未压缩约 43 KB/帧。5 Hz 约 215 KB/s，加协议开销仍适合局域网。队列永远保留最新帧，网络拥堵时丢旧帧，禁止为了完整性累积延迟。

### 5.2 关键帧策略

满足任一条件才发送新的融合帧：

- 距上个融合位姿平移至少 5 cm；
- 旋转至少 4 度；
- 超过 250 ms 且有新的 Raw Depth；
- 前方风险发生变化。

同时限制 10 Hz 上限。站定时不重复写入相同深度，以免把噪声累积成实体。

## 6. 三维地图

### 6.1 地图层

后端同时维护：

1. **TSDF 静态层**：墙、家具、门框、楼梯等表面轮廓；
2. **占据/自由空间层**：深度射线命中前为空闲，命中附近为占据；
3. **动态层**：人、宠物、移动椅子等短生命周期障碍；
4. **3D ESDF**：每个自由体素到最近障碍的距离和梯度；
5. **语义对象层**：YOLO 名称、三维位置、尺寸、速度和可信度；
6. **可观测性层**：已观测、未知、过期区域，未知不能当作自由空间。

默认体素 5 cm；近身 2 m 内可保留更高权重，地图半径先限制为手机周围 8~12 m。地图更新遵循新观测覆盖旧证据、正反证据累积和时间衰减，解决“之前标红后永远不变”的问题。

### 6.2 门框与窄路

地图只保存实际表面，不在融合阶段把障碍粗暴向外膨胀。规划时才使用人体模型做配置空间碰撞：

- 默认身体半径 30 cm；
- 额外定位/深度误差余量 10~15 cm，随跟踪质量动态变化；
- 左右门框保持为两条真实障碍，中间宽度达到阈值时仍能生成通过走廊；
- 头顶净空按约 1.9 m 检查；
- 膝盖以下障碍、腰部障碍、头部障碍分别标注，不压成一层红块。

## 7. 地面、台阶与楼梯

系统从局部 TSDF mesh/法向和重力方向提取支撑面：

- 可走平面：坡度、粗糙度、宽度和连续性达标；
- 上行台阶：连续高度上升，估计第一级距离、踏步高度/深度、宽度和方向；
- 下行台阶：前方支撑面消失且下方重新出现；
- 落差/孔洞：射线已观测但脚下没有支撑面；
- 未扫描：只标未知，不能误报成落差，也不能报可走。

楼梯采用专用动作状态，不能只交给普通 A*：到第一级前要求停下确认并扶稳；每级只给短距离动作；下楼比上楼使用更保守的确认门限。初版只做楼梯识别和接近提醒，通过专项真机验收后再开放逐级引导。

## 8. 路线规划

### 8.1 目标表达

目标可来自三类输入：

- 当前局部画面中的对象，例如“走到门口”；
- 已建家庭地图的地点，例如“卫生间”；
- 用户指定方向，例如“继续往前找可走区域”。

跨会话家庭导航需要视觉重定位。仅保存几何轮廓很难稳定判断“这是家里哪个位置”，因此家庭地图必须额外保存少量灰度关键帧/局部视觉描述子和三维地标；它们只用于重定位，不参与颜色描述。

### 8.2 人体体积与候选走廊

规划对象不是一个点，而是有半径、高度和脚下支撑要求的竖直胶囊体。每个候选动作必须同时满足：

- 身体体积与 ESDF 障碍距离大于动态安全余量；
- 脚下连续存在可靠支撑面；
- 路线不穿过未知空间；
- 坡度、台阶参数和净空在允许范围；
- 动态障碍的预测位置不与走廊冲突。

先在局部导航图上做增量 A*/D* Lite，随后用 ESDF 梯度把路径推离障碍并做曲率平滑。返回的是未来 2~4 m 的短走廊，不是一次性整屋折线。手机移动约 20 cm、方向偏离约 10 度、地图改变或出现动态障碍时重规划。

### 8.3 路线置信度

电脑为每段路线返回：

- 起点和路线点的 `map` 坐标；
- 走廊宽度和最近障碍距离；
- 支撑面/楼梯类型；
- 方向、预计距离、动作类型；
- 地图版本、生成时间、有效期；
- 几何、定位、动态障碍三项置信度；
- 停止原因或补扫方向。

任何关键置信度不足时不下发“向前走”，改为“请停下，将手机稍微向下/向左补扫”。

## 9. 手机如何知道该怎么走

### 9.1 `RouteFollower`

手机收到路线后，不等待电脑逐步遥控，而是用当前 ARCore 位姿在本地以 30~60 Hz 执行：

1. 将手机位置投影到路线中心线；
2. 计算下一个 0.6~1.0 m 前视点的相对方向；
3. 判断用户是否转向、前进、偏离或停止；
4. 只有动作状态改变或达到距离节点才播报；
5. 位移达到节点后自动切换下一段；
6. 偏离走廊、地图版本变化或局部急停时请求重规划。

手机本地保存最近 2~4 m 路线，不保存“道路永久安全”的结论。路线超时后立即失效。

### 9.2 动作状态机

```text
WAIT_MAP
  -> ALIGN（请向左/右转）
  -> ADVANCE（向前约 N 米）
  -> APPROACH_TURN（前方约 N 米后转向）
  -> TURN（向左/右转）
  -> BYPASS（沿候选走廊绕行）
  -> ARRIVED

任意状态
  -> LOCAL_STOP（手机近身急停）
  -> SERVER_STOP（电脑发现新障碍/落差）
  -> RESCAN（定位、脚下或地图证据不足）
  -> RELOCALIZE（ARCore 坐标重置或跨会话定位失败）
```

示例播报：

- “向右转一点”；
- “方向正确，向前约一米”；
- “前方约八十厘米有椅子，路线向左绕行”；
- “继续沿左前方走约一米”；
- “已绕过，方向正确，继续前进”；
- “脚下区域不完整，请停下，将手机稍微向下补扫”；
- “网络或定位中断，请停下确认”。

震动编码只表达紧急程度和转向，不承载复杂距离：急停长震，左/右转使用左右节奏，普通节点短震。语音由现有 `SpeechArbiter` 统一调度，急停可抢断，普通进度不得重复抢断。

## 10. 实时性预算

目标局域网端到端 P95：普通路线更新不超过 350 ms，近身急停不超过 200 ms。

| 环节 | P95 预算 |
|---|---:|
| 手机采集和打包 | 20 ms |
| Wi-Fi/USB 上行 | 40 ms |
| TSDF/占据融合 | 35 ms |
| ESDF 与地面更新 | 45 ms |
| 局部规划 | 60 ms |
| 下行 | 40 ms |
| 手机状态机和播报提交 | 30 ms |
| 余量 | 80 ms |

后端每个响应记录分段耗时；若 P95 超预算，优先降低关键帧频率或地图半径，不能排队处理旧帧。语音合成本身不计入几何判断延迟，急停可先震动再播报。

## 11. 失效与降级

手机每 100 ms 检查数据新鲜度：

- 路线超过 700 ms 未更新：只允许沿已确认走廊短暂执行；
- 超过 1.5 s：停止前进引导并提示连接不稳定；
- ARCore tracking 非 TRACKING 超过 500 ms：停止；
- 地图与当前 session/world transform 不一致：停止并重新对齐；
- 手机本地发现 1.2 m 内新障碍：立即覆盖服务器前进指令；
- 服务器重启/session ID 变化：旧路线全部作废；
- 网络断开：退回现有纯本地识别、近身障碍和补扫提示，不继续在线导航。

## 12. 实施阶段

### 阶段 A：数据闭环与回放

1. 固化协议、坐标和时间测试；
2. 手机发送新 Raw Depth、Confidence、Pose、Intrinsics、YOLO；
3. 后端录制和逐帧回放；
4. 可视化相机轨迹与单帧深度投影；
5. 验证静止墙面不会随手机移动漂移。

### 阶段 B：实时三维融合

1. 接入 nvblox TSDF/占据/3D ESDF；
2. 实现动态衰减和补扫纠错；
3. 识别地面、净空、悬空障碍和门洞；
4. 手机显示简化俯视/侧视调试图，但面向视障用户的主交互仍为语音和震动。

### 阶段 C：局部闭环导航

1. 人体体积碰撞检查；
2. 生成 2~4 m 短走廊；
3. 手机 `RouteFollower` 和语音状态机；
4. 新障碍、偏航、补扫和恢复；
5. 普通平地、门洞和静态家具绕行验收。

### 阶段 D：楼梯专项

1. 上楼、下楼、单级台阶、落差分开建模；
2. 先启用停下/接近提醒；
3. 在有人保护的封闭环境完成专项数据集和真机验收；
4. 达标后再开放逐级动作引导。

### 阶段 E：家庭地图与跨会话定位

1. 地图持久化和版本管理；
2. 灰度关键帧/局部视觉特征重定位；
3. 房间与目标点标注；
4. 从卧室到卫生间的全局路径，局部仍由实时三维地图纠偏。

## 13. 验收条件

### 13.1 自动化与数据回放

1. 已知深度、内参和位姿能还原到预期世界点，坐标误差不超过 2 cm（合成数据）；
2. 旧 Raw Depth 不重复融合；乱序包不回退地图时间；
3. 新的自由空间观测能降低旧占据证据，动态障碍离开后可消退；
4. 门框之间净宽足够时产生候选走廊；不足时拒绝；
5. 未知空间、无支撑面和占据空间均不能生成普通前进路线；
6. 路线过期、session 改变、定位丢失立即作废；
7. 手机偏离路线后停止旧动作并请求重规划；
8. 本地急停优先级高于服务器前进指令；
9. 网络拥堵时丢弃旧帧，队列延迟不持续增长；
10. 录制数据可确定性回放并输出每段延迟。

### 13.2 室内真机

1. 平地 10 m 往返，静态轮廓无明显重影，手机轨迹不中断；
2. 宽门洞 20 次通过，不能持续把门框封成整面障碍；
3. 椅子移开后重新扫描，原障碍区域在规定时间内更新为候选可走；
4. 椅子突然进入路线，本地 200 ms 目标内先震动/停止，服务器随后重规划；
5. 绕过障碍后能明确播报“已绕过，继续前进”；
6. 手机平视时，历史地图仍保留已经可靠扫描过的脚下支撑面；新区域脚下未知时要求补扫；
7. 普通路线更新 P95 不超过 350 ms，连续运行 20 分钟无积压和显著内存增长；
8. 断网、后端重启、ARCore 跟踪丢失均不会继续播放旧的前进指令；
9. 上下楼梯初期只验收正确识别、方向和第一级距离，不把它计入普通平地导航通过率。

### 13.3 准确性指标

- 0.5~3 m 静态表面距离中位绝对误差目标不超过 15 cm；
- 平地支撑面误判为障碍的比例低于 5%；
- 已充分扫描的宽门洞封堵率低于 5%；
- 近身实体障碍漏报率在专项测试集中低于 1%；
- 下行台阶漏报单独统计，未达到专项门限前不开放自动下楼引导；
- 所有指标必须同时给出测试场景、样本数和置信区间，不能只展示成功视频。

## 14. 第一轮开发边界

第一轮只完成阶段 A 和阶段 B 的最小闭环：手机流式发送、电脑实时生成可更新的粗三维轮廓/ESDF、电脑把地图质量和前方走廊状态返回手机。暂不承诺整屋跨会话定位和楼梯逐级导航。

当且仅当坐标、延迟、动态更新和门洞测试达标后，再接入 `RouteFollower`。这样可以把“地图错了”和“导航错了”分开定位，避免语音看似完整但底层几何不可靠。
